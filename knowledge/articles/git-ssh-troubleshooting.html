Git SSH 连接排障

当 git push 卡在 SSH 握手、22 端口被限制或代理链路不稳定时，先把“Git 问题”和“SSH 连接问题”分开验证。

GitSSHGitHubPort 443

1. 先确认远端协议

git remote -v

如果远端是 git@github.com:owner/repo.git，当前走的是 SSH；如果是 https://github.com/...，则应该排查 HTTPS / 代理链路，而不是 SSH 配置。

2. 直接测试 SSH，并打开详细日志

ssh -vT git@github.com

重点看日志停在哪一层：DNS、TCP 建连、密钥交换、Host Key、认证还是远端主动断开。kex_exchange_identification 一类错误通常发生在认证之前，因此先不要反复换 SSH key。

3. 22 端口不稳定时测试 GitHub SSH 443

ssh -T -p 443 git@ssh.github.com

如果 443 可以连通而默认 SSH 不行，可以把 GitHub 主机映射到 ssh.github.com:443。

# ~/.ssh/config
Host github.com
    HostName ssh.github.com
    Port 443
    User git

配置后重新验证：

ssh -vT git@github.com

4. 不想改配置时，用一次性命令验证

GIT_SSH_COMMAND="ssh -o HostName=ssh.github.com -p 443" git push

这适合确认“改走 443 是否能解决问题”。如果临时命令稳定，再决定是否写入 ~/.ssh/config。

5. 确认 SSH 实际读取了什么配置

ssh -G github.com | grep -E 'hostname|port|user|identityfile'

ssh -G 会打印最终合并后的配置，比单纯打开 ~/.ssh/config 更可靠，因为系统级配置、Include 和 Host 匹配都可能改变结果。

6. 把网络、认证、仓库权限分开

排障顺序
  • 网络：SSH 是否能建立连接和完成 key exchange。
  • 认证：ssh -T 是否识别到 GitHub 账号。
  • Git：git remote -v 是否指向预期仓库。
  • 权限：当前账号是否对目标仓库具有 push 权限。

只有前一层通过后再进入下一层，能避免把网络中断误判成密钥问题，也避免在 SSH 正常时继续修改代理。

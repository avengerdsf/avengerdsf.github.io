1. 把 Linux 知识分成三层

面对一个系统问题时，最容易出现的问题是命令越记越多，但下次仍然不知道从哪里开始。更稳定的做法是按三层组织：

  • 查询层：先拿到事实，例如进程、端口、磁盘、内核、驱动和日志当前是什么状态。
  • 诊断层：建立因果关系，例如某个端口被谁占用、某个内核模块是否加载、某个服务为什么启动失败。
  • 操作层：修改配置、切换版本、重启服务或封装脚本，并保留可恢复路径。

2. 高频命令应该记录“用途 + 上下文”

只记录 ps -ef、tar -xzf 或 grep 本身价值有限。更适合知识库的形式是把问题和命令绑定起来：

# 查找进程并确认 PID
ps -ef | grep process_name

# 查看端口占用
ss -lntp

# 解压 tar.gz
tar -xzf archive.tar.gz

# 查看当前内核
uname -r

这样搜索“PID”“端口”“解压”“内核”时可以直接落到解决路径，而不是命令列表。

3. 调试命令要形成最短闭环

以 GDB 为例，笔记最好围绕“我要观察什么”来组织，而不是按命令字母顺序整理：

  1. 设置断点并运行到目标位置。
  2. 通过单步、变量打印和调用栈定位状态变化。
  3. 多线程问题再进入线程列表、线程切换和 scheduler locking。
  4. 把重复动作写进 commands，减少人工操作。

4. 环境问题要保留“当前状态”

驱动、内核、代理、WSL 网络这类问题都高度依赖环境。知识条目里应该同时记录版本、关键配置和验证命令。否则几个月后只剩下一条“执行这个命令就好了”，很难判断是否仍适用。

  • 系统 / 内核版本。
  • 驱动或工具版本。
  • 关键配置文件位置。
  • 修改前后的验证命令。
  • 回滚方式。

5. 重复三次以上，就考虑工具化

知识库解决“下次怎么做”，工具仓库解决“下次不用手做”。当一个流程稳定且重复出现，可以从笔记升级成脚本、C++ 小工具或配置生成器。这也是知识库与 ubuntu_toolbox、Tmux-generator 之间应该形成的关系。

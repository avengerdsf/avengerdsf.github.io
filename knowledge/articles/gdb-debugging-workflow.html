GDB 调试工作流

不要把 GDB 记成命令表。更实用的方式是按“断点 → 观察 → 线程 → 自动化”建立最短定位闭环。

GDBC / C++Shared LibraryThreads
最小三步：

共享库符号尚未加载时先允许 pending breakpoint；程序启动后再对目标函数打断点；命中后用 n / s / finish 控制观察粒度。

1. 先把断点打到正确位置

# 允许目标符号尚未加载时保留断点
set breakpoint pending on

# 文件 + 行号
b runtime.cc:4873

# 函数
b Runtime::BinaryLoad

# 启动程序
run

如果目标函数位于运行时才加载的 .so 中，pending breakpoint 可以避免因为当前找不到符号而直接丢掉断点。

2. 命中后控制观察粒度

# 下一行，不进入函数
n
# 单步进入函数
s

# 跑到当前函数返回
finish

# 继续运行
c

需要看调用函数内部状态时用 s，只关心当前层逻辑时优先 n；进入太深后用 finish 回到调用点。

3. 观察变量和调用栈

# 打印变量
p value

# 十六进制打印
p/x address

# 变量变化时停住
watch value

# 当前调用栈
bt

watch 适合回答“是谁改了这个值”，而 bt 适合回答“程序为什么走到这里”。二者解决的是不同问题。

4. 把重复动作写进 commands

commands 1
  silent
  p a
  bt
  c
end

上面的 1 是断点编号，不是函数名。每次 1 号断点命中后，GDB 会自动执行打印变量、打印调用栈并继续运行。

5. 多线程问题先看全局，再锁定单线程

# 查看所有线程
info threads

# 切换到 3 号线程
thread 3

# 打印全部线程调用栈
thread apply all bt

# 单步时只让当前线程运行
set scheduler-locking on

# 恢复正常线程调度
set scheduler-locking off

单步过程中其他线程继续执行会导致状态变化时，可以临时打开 scheduler locking；定位完成后要及时关闭。

6. 让输出更适合长时间调试

# 禁止分页，避免脚本/长输出被 --More-- 打断
set pagination off

如果需要临时验证返回值分支，还可以使用 return 0 或 return 1 强制当前函数返回，但这会改变程序行为，只适合有明确目的的调试实验。

定位顺序
  • 先确认断点是否真的命中目标代码。
  • 再确认输入参数和关键状态。
  • 再看调用栈判断上游路径。
  • 多线程问题最后进入线程切换和调度锁定。
  • 重复观察动作写进 commands。

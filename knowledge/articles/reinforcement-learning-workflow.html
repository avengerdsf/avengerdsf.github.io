强化学习工程工作流

机器人强化学习工程不应该只有一个训练脚本。模型资源、环境、奖励、算法配置、训练入口和回放入口需要形成清晰边界，才能持续调试和迁移。

公开示例：

agibot_rl_mjlab ↗ 已经把训练入口、回放入口、任务注册、机器人配置、环境配置和 PPO 配置拆开，本页基于这种工程结构说明各部分应该承担什么职责。

1. 先拆清楚六个工程层次

  1. 机器人资源：模型文件、关节/body 命名以及与机器人本体有关的常量。
  2. 任务注册：定义可被训练脚本发现和调用的任务名称。
  3. 环境配置：观测、动作、命令、奖励、终止条件和场景参数。
  4. 算法配置：PPO 网络结构、学习率、batch、clip、折扣因子等训练参数。
  5. 训练入口：创建环境、加载算法配置、开始采样与优化、保存 checkpoint。
  6. 回放入口：加载固定 checkpoint，在确定性或受控条件下观察策略行为。

2. 训练入口只负责“组织流程”

训练脚本不适合堆积机器人参数和奖励公式。它应该更多承担 orchestration：解析参数、创建任务、启动 runner、设置日志和 checkpoint。这样切换机器人或任务时，训练入口本身基本不需要改。

robot config
    ↓
environment config
    ↓
PPO config
    ↓
train.py → checkpoint
                 ↓
              play.py

3. 奖励和观测要能独立定位

训练效果异常时，最常见的问题往往不是“PPO 不行”，而是观测、命令、奖励和终止条件之间存在冲突。工程上应保证这些定义集中在环境配置附近，并能明确回答：

  • 策略到底看到了哪些状态？
  • 动作映射到哪些关节或控制量？
  • 主奖励与约束型奖励是否在量级上互相覆盖？
  • episode 为什么结束，结束是否会扭曲策略行为？

4. 回放不是“看起来能走”就结束

play.py 的价值是把训练中的随机性拿掉，固定策略、固定模型和可控命令，观察行为是否符合预期。对机器人项目来说，回放还应该承担 Sim-to-Sim 前的接口核对：关节顺序、动作缩放、初始姿态、控制周期和观测归一化必须一致。

5. 从训练到 MuJoCo 验证

跨仿真器迁移时，不应只复制网络权重。真正需要对齐的是策略输入输出语义：

  • 观测字段的顺序、坐标系与单位。
  • 动作缩放、关节顺序与 PD/力矩接口。
  • 控制频率与 action decimation。
  • 默认姿态、重力方向和四元数约定。
  • 训练时存在的归一化或历史堆叠。

只要这些语义边界清晰，训练框架和验证仿真器就可以分别演进，而不会把迁移逻辑散落到各个脚本。
